# v3 프로젝트 안정성 정적 진단

기준: `v3` / `9e3f7ad`. 프론트엔드, 백엔드, DB 마이그레이션, PC 하드웨어 런타임과 저장·전송 경로를 검토했다. 연동 확인 목적으로 저장소 밖 `Raspberry_Pi/robot_push_test`의 Pi 서버와 Arduino 펌웨어도 일부 확인했다.

사용자 요청에 따라 테스트, 빌드, 애플리케이션 실행, DB 접속, 로봇 제어를 수행하지 않았다. 아래 발생 조건과 영향은 코드 경로에 근거한 정적 판단이며 이번에 재현한 결과가 아니다. 기존 진단 문서는 참고하되 주요 항목은 현재 코드에서 재확인했다. 실행 코드는 변경하지 않았다.

## 전체 판단

핵심 구조를 전면 교체할 필요는 없다. 영상·모터 통신 분리, 최신 프레임 사용, 모터 명령 유효기간, 재연결 세션 구분, 제거 확인 조건, 결과 재전송은 유지할 가치가 있다. 가장 큰 개선 대상은 **서버·화면·로봇의 상태 일치**, **실패한 요청의 종료와 복구**, **관측 시각과 사건 식별자 보존**이다.

현재 상태를 실물 안정성 검증 완료로 판단할 수는 없다. 특히 이송 결과, 재시작, 지연 이벤트, 제어 스레드 장애의 처리에는 아래 보완이 필요하다.

## 우선 수정 대상

### 1. 이송 완료의 의미가 계층마다 다름 — 우선순위 1

- 근거: `backend/src/main/java/com/deni/backend/device/DeviceMessageService.java:78`, `backend/src/main/java/com/deni/backend/operation/OperationService.java:46`, `frontend/src/pages/HazardLocation.tsx:118`, `hardware/care_controller.py:200`.
- 서버는 이송 성공 후에도 위험을 `ACTIVE`로 유지한다. 화면은 `relocationState=done`이면 처리 완료처럼 표시하고, 로봇은 해당 라벨의 차단을 해제한다.
- 결과: 화면 재진입 시 위험이 다시 나타날 수 있고, 이송 후 일시정지→재개는 서버의 ACTIVE 검사로 거절될 수 있다. 이송된 물체를 다시 관측하면 로봇이 다시 차단할 가능성도 있다.
- 제안: 서버에 임시 안전 상태를 명시적으로 저장하고, 그 상태의 주행 차단 여부를 결정한다. 같은 정책을 화면과 로봇에 적용한다. 같은 종류의 모든 물체를 일괄 무시하는 방식은 피한다.

### 2. 서버 재시작이 실제 제거 없이 위험을 완료 처리함 — 우선순위 1

- 근거: `backend/src/main/resources/application.properties:29`, `backend/src/main/java/com/deni/backend/common/DemoSessionReset.java:30`.
- `DEMO_RESET_ON_STARTUP` 기본값은 true이고 시작 시 ACTIVE 위험을 모두 RESOLVED로 바꾼다. 미완료 명령도 일괄 만료 처리한다.
- 결과: 실제 물체·로봇 차단 상태와 서버 기록이 달라진다. 로봇이 나중에 보고한 결과가 이미 만료된 명령에 해당하여 거부될 수도 있다.
- 제안: 정상 실행에서는 자동 초기화를 끄고, 시연 초기화는 명시적인 별도 작업으로 분리한다. 단순히 설정만 끄면 이송 ACTIVE 정책과 UNKNOWN 요청 문제는 남으므로 1·3·4번을 함께 정리한다. PC 재시작 시 메모리 차단 상태가 사라지는 문제도 서버 미처리 사건과 동기화하여 해결해야 한다.

### 3. 전달되지 않는 요청이 계속 대기할 수 있음 — 우선순위 1

- 근거: `OperationService.java:83`의 직접 제거 요청, `:151`의 `queueAction`, `DeviceCommandDispatcher.java:20`의 delivery 기준 만료 처리.
- 직접 제거는 이송과 달리 `requireDelivery`를 호출하지 않는다. 최신 정지 보고는 남아 있지만 제어 연결이 없는 경우, 요청만 저장되고 delivery 행 생성은 생략될 수 있다.
- 결과: 조회는 PENDING/NOT_CONNECTED를 반환하며 자동 만료 대상에서도 빠진다. 일반 pause 요청에도 유사한 접수·전달 분리 경로가 있다.
- 제안: 모든 접수 요청에 전달 기록과 만료를 보장하거나 전달 불가 요청을 명확히 거절한다. 정지 요청은 접수 가능성과 실제 정지 확인을 구분하여 안내한다.

### 4. 명령 예외와 장기 단절의 종료·복구 경로 부족 — 우선순위 1

- 근거: `hardware/bridge.py:219`, `hardware/care_runtime.py:117`, `hardware/care_controller.py:258` 및 `:300`, `OperationService.java:153`.
- 실행 또는 결과 검증 예외가 발생하면 started_commands만 남고 pending_results에 도달하지 않을 수 있다. 상위 처리기는 예외를 로그로 남긴다.
- 모터가 준비되지 않으면 제어 함수가 작업 제한 시간 검사보다 먼저 반환한다. 모터가 장기간 돌아오지 않으면 PC의 명령 대기도 계속될 수 있다.
- 서버는 기한 경과 후 UNKNOWN으로 전환하지만, UNKNOWN은 다음 안전 처리 요청을 막는 busy 상태에 포함된다.
- 제안: 연결 준비 여부와 독립적으로 작업의 기한을 검사하고, 예외에도 실행 여부를 보존한 결과를 영속 저장한다. UNKNOWN에는 정지 확인→현재 상태 조회→작업 정리의 복구 경로를 둔다. 결과가 불명확한 물리 동작을 자동 재실행하지 않는다. 스레드를 기다리는 비동기 작업을 취소하는 것만으로 실제 제어가 취소되는 것은 아니므로 취소 신호를 제어기까지 연결한다.

### 5. 제거 전 촬영한 이미지가 제거 후 재감지로 기록될 수 있음 — 우선순위 1

- 근거: `hardware/detection/event_store.py:24`, `hardware/bridge.py:106`, `DetectionUploadService.java:49`, `backend/src/main/resources/db/migration/V7__create_robot_input_tables.sql:50`.
- 로컬에는 촬영 시각이 있지만 업로드 필드로 전달되지 않는다. DB는 감지 시각을 수신 시각으로 생성한다.
- 조건: 촬영→통신 지연→제거 완료→과거 이미지 업로드. 프론트의 완료 시각 비교로도 새 위험처럼 보일 수 있다.
- 제안: `capturedAt`, `receivedAt`, `sessionId`, `frameSequence`, `eventId`를 끝까지 유지한다. 촬영 시각은 허용 오차를 검증하고, 같은 세션 내 순서는 sequence로 보강한다. 처리 이전 관측은 이력에 저장하되 새 위험으로 승격하지 않는다. API와 DB 트리거를 함께 변경해야 한다.

### 6. 제어 스레드 중단이 최신 상태 보고로 가려질 수 있음 — 우선순위 1

- 근거: `hardware/care_runtime.py:100`, `:126`, `:215`, `:220`, `hardware/bridge.py:144`.
- 제어 스레드가 예외로 종료되어도 메인 루프는 스레드 생존 여부를 확인하지 않는다. 상태 보고는 별도 스레드이므로 계속 실행될 수 있다.
- `operationState`와 `taskState`는 마지막 제어 상태를 사용하지만, 전송 시 sampledAt은 새 시각으로 붙는다. 모터 스레드가 명령 만료에 따라 정지하면 과거 RUNNING과 현재 STOPPED가 함께 보고될 가능성이 있다.
- 제안: 제어 루프 완료 시각과 상태 revision을 저장하고, 제어 루프가 오래 멈췄으면 보고를 FAULT/UNKNOWN으로 전환한다. 핵심 스레드 사망 시 정지·진행 명령 정리·프로세스 종료를 감독하는 경로를 둔다. 모터 명령 만료에 의한 정지 자체는 현재 구현의 장점이며 유지한다.

## 다음 순서로 보완할 사항

### 7. 저장 이력과 전송 대기열이 분리되어 누락 가능 — 우선순위 2

- 근거: `hardware/detection/event_store.py:31` 이후 `:42`, `hardware/detection/worker.py:37`.
- 사진/로컬 DB 저장 후 다른 DB에 업로드 대기열을 등록한다. 두 번째 단계 실패 시 로컬 이력만 남을 수 있다. EventStore 최초 생성 실패 후 자동 재생성 경로도 없다.
- 제안: 하나의 트랜잭션으로 이벤트와 전송 상태를 저장하거나, 같은 eventId로 누락 대기열을 복원한다. 저장 실패와 업로드 거절은 로봇 상태·화면에 표시한다. 이미 전송된 이미지와 거절 이벤트의 보관 한도도 둔다.

### 8. 인식 안정화는 최근 연속 프레임이 아닌 양성 관측 누적 — 우선순위 2

- 근거: `hardware/detection/stabilization.py:17`, `hardware/detection/risk_engine.py:67`.
- 미검출 프레임이 투표에 들어가지 않으므로 같은 추적 대상의 간헐적 검출이 누적될 수 있다. v3의 후보/확정 차단 분리는 개선됐지만 확정 기준의 시간적 의미는 그대로다.
- 제안: 유효 관측의 시간 창과 허용 공백을 정의하고 정상 미검출도 반영한다. 카메라 오류는 미검출로 세지 않는다. 임계값 조정과 인식 성능 평가는 이후 실영상 검증이 필요하다.

### 9. 아이 프로필 화면 진입이 로봇의 감지 귀속을 변경 — 우선순위 2

- 근거: `frontend/src/pages/RegisteredHome.tsx:135`, `DeviceService.java:97`, `DetectionUploadService.java:34`.
- 다른 아이 홈을 열면 활성 아이가 변경된다. 감지 저장은 업로드 시점의 활성 아이를 사용한다.
- 결과: 여러 탭이나 지연 업로드에서 촬영 당시와 다른 아이에게 위험이 귀속될 수 있다.
- 제안: 화면 조회와 로봇 운용 프로필 변경을 분리하고, 진행 중 작업이 있을 때 전환 정책을 둔다. 관측에 촬영 당시 세션 귀속을 기록한다. 활성화 실패 후 ref를 비우는 것만으로 effect 재실행이 보장되지 않는 점도 수정한다.

### 10. 화면의 진행 요청 복원과 응답 순서 관리 부족 — 우선순위 2

- 근거: `HazardLocation.tsx:105`, `:207`, `:234`, `RegisteredHome.tsx:24`, `frontend/src/services/operations.ts:35`.
- actionId는 컴포넌트 메모리에만 있고 화면 이탈 후 서버 작업을 복원하지 않는다. 조회 실패는 메시지 없이 반복되며, 사용자 재시도에는 새 멱등키가 생성된다.
- 상세 응답의 최신 판단은 detectedAt만 사용한다. 감지 시각이 같은 ACTIVE/RESOLVED 응답이 역순 도착하면 상태가 되돌아갈 수 있다.
- 제안: 현재 작업 조회 API를 제공하고 재진입 시 복원한다. 동일 사용자 의도의 멱등키를 보존한다. 응답에는 서버 version/updatedAt을 포함하고 오래된 응답을 버린다. 조회 실패는 작업 실패와 구분하여 표시한다.

### 11. 백엔드의 모든 메시지가 정상 연결 증거로 사용됨 — 우선순위 2

- 근거: `hardware/bridge.py:239`, `DeviceSocketHandler.java:42`, `hardware/care_runtime.py:91`.
- JSON 검증 전에 contact_handler가 호출되어 ERROR나 잘못된 메시지로도 3초 타이머가 갱신된다. 따라서 연결 생존과 상태 보고의 정상 수락은 서로 다르다.
- 제안: 연결 생존 시각과 정상 수락된 상태 보고 시각을 분리하고, 준비 상태를 판단하는 정책을 명시한다. 결과 거절은 messageId와 오류 사유를 돌려주고, 영구 거절 결과는 무한 재전송 대신 복구 대기로 전환한다. receipts map도 제한·정리한다.

### 12. 배포 단위가 PC 저장소와 Pi/펌웨어로 나뉨 — 우선순위 2

- 근거: `git ls-files` 기준 deni에는 pi_robot_server.py와 Arduino .ino가 없다. 실제 연동 소스는 상위 작업 공간의 별도 경로에 있다.
- v3의 HTTP `/focus`는 Pi 서버 지원이 필요하다. PC 코드만 clone/pull하면 대응 Pi 버전이 확보되지 않는다.
- 제안: Pi 서버·펌웨어를 버전 관리 범위에 포함하거나 별도 저장소 커밋을 배포 명세에 고정한다. PC/Pi/펌웨어 프로토콜 버전과 지원 기능을 연결 시 교환한다. Python은 가상환경 폴더 복사 대신 재생성하고 검증된 의존성 버전을 기록한다. 가중치는 해시·클래스 목록으로 식별한다.

| 물리 구동 | 시간 기반 회전·확보, ACK는 명령 수신 증거이며 거리·회전각·물체 확보 센서가 아님 | 현재 문구에서 실측 성공과 구분. 향후 엔코더/IMU·범퍼·구동부 전원 차단 등 피드백 검토 |

## 권장 개선 순서

1. **상태 계약 확정:** 위험 상태, 작업 상태, 로봇 상태를 분리하고 각 상태의 주행 차단 여부를 표로 고정한다. 특히 이송 임시 완료와 결과 미확정을 먼저 결정한다.
2. **실패 경로 정리:** 모든 접수 요청에 전달 기록·기한·결과를 보장하고, 장기 단절과 제어 스레드 예외를 정리한다. 재시작은 현재 미처리 사건을 확인한 정지 상태에서 시작한다.
3. **사건 정보 보존:** 촬영 시각, 수신 시각, 세션, 프레임 순서, 이벤트 ID를 끝까지 연결하고 저장/전송 누락을 복구한다.
4. **화면을 서버 상태와 일치:** 진행 요청 복원, 응답 버전 비교, 조회 장애 표시, 임의 좌표 제거를 적용한다.
5. **배포와 관측성 정리:** PC/Pi/펌웨어의 대응 버전을 고정하고 공통 로그에 eventId/hazardId/commandId/sessionId를 넣는다. 제어 루프 지연, 추론 지연, 상태 수락 지연, 업로드 적체를 별도로 표시한다.

현재 테스트를 수행할 수 없으므로 모터 시간·초점·오차 임계값을 추가로 조정하는 것보다 상태 계약과 실패 처리 설계를 먼저 확정하는 편이 적절하다. 정적 검토만으로 수정 후 안정성을 보장할 수는 없다.

## 추후 검증 가능한 시점의 합격 기준 제안 — 이번에는 미실행

- 이송 완료 후 화면 재진입·일시정지·재개에서 서버와 로봇의 판단이 일치한다.
- 서버 또는 PC 재시작만으로 위험이 사라지거나 자동 주행하지 않는다.
- 모터가 120초 이상 복구되지 않아도 진행 요청이 영구 대기로 남지 않는다.
- 제어 스레드를 중단하면 모터 출력 만료와 함께 화면에도 제어 장애가 표시된다.
- 제거 전 촬영된 지연 이미지가 제거 후 새 위험을 만들지 않는다.
- 업로드 대기열 등록 실패 후 같은 eventId로 누락 이벤트가 복구된다.
- 결과 응답 유실·화면 재진입·사용자 재시도에서 같은 물리 작업이 중복 실행되지 않는다.
- 프로필 전환 및 다중 동일 종류 물체에서 사건 귀속과 제거 범위가 유지된다.
