# 요구사항 대조 및 재감지 진단

점검일: 2026-09-24. 대상: `deni/frontend`, `deni/backend`, `deni/hardware`.

제공된 TKS 8개, 취소선이 없는 FR 전체, NFR 28개를 기준으로 점검했다. 여기서 **구현 확인**은 코드 경로가 존재한다는 뜻이며 실기기 성능이나 운영 적합성 인증을 뜻하지 않는다. 실제 시연 영상·당시 로그·DB 이벤트를 확보하지 않았으므로 특정 시연 오보의 단일 원인은 확정하지 않았다. 기존 미커밋 변경은 유지했고, 운영 DB·로봇에는 명령을 보내지 않았다.

전체 판정은 **부분 일치**다. 아이 등록, 프로필, 감지 저장, 홈·상세 조회, 처리 요청, 월간 리포트의 뼈대는 있지만, 재감지의 사건 순서, 실제 위치, 푸시, 사용자 권한, 상태 복원, 데이터 보관에서 차이가 있다. 파일 수를 줄이는 것보다 먼저 **현재 관측 / 미처리 위험 기록 / 처리 요청 / 처리 이후 새 사건**의 의미를 분리해야 한다.

### 왜 “지금 물체가 없다”와 ACTIVE가 함께 보이는가

ACTIVE는 **현재 카메라 검출 여부**가 아니라 **아직 처리 완료되지 않은 위험 기록**이다. 기존 코드는 확정 위험이 시야에서 사라져도 사용자 재확인 성공 전에는 정지를 유지한다. 이는 자동 성공을 방지하는 동작이지만, 화면이 현재 검출과 과거 미처리를 같은 문장으로 표현하면 오보로 느껴진다. 순간 인식으로 앱에 없는 차단이 생기던 경로는 이번에 수정했다. 확정 오탐 자체, 지연 업로드, 카메라 시야 밖 물체까지 해결한 것은 아니다.

현재 재확인은 **카메라의 유효 프레임에서 해당 라벨이 2초 이상 보이지 않음**과 모터 응답을 사용한다. 공간 전체의 제거 증명은 아니므로 시야·동일 라벨 다중 객체·가림 조건을 실기기 시험에 반드시 넣어야 한다.

## 5. 구조 단순화 방향

이번에는 재감지의 프론트 이중 판정과 과거 투표 재사용을 제거하는 범위로 수정했다. 실행 중인 계약과 기존 수정 사항을 보존하기 위해 디렉터리 이동·DB 구조 변경·시연 데이터 초기화는 수행하지 않았다.

1. **서버가 위험 사건과 처리 상태의 기준을 소유한다.** 감지에는 eventId, deviceId, captureAt, receivedAt, sessionId, sequence를 보존하고, 처리에는 actionId와 확인된 완료 시각을 둔다. 완료 전 촬영·지연 도착 이벤트는 기록 보관과 ACTIVE 생성 여부를 구분한다. 실제 객체 동일성 없이 라벨만 같은 경우 “같은 종류의 물체 감지”라고 표현한다.
2. **프론트의 재감지·위험도 재계산을 축소한다.** 서버가 `redetectedAfterActionId` 등 판정 근거를 반환하게 하고, 화면은 이를 표시한다. `HazardLocation`의 실제 상태와 mock Flow를 별도 컴포넌트/어댑터로 분리한다. 진행 중 처리 요청은 서버에서 복원한다.
3. **하드웨어는 관측과 모터 제어에 집중한다.** 임시 후보는 정지 후 관측하고, 확정 사건만 지속 차단한다. 라벨 set 대신 서버 사건과 연결할 최소 식별자를 설계한다. 네트워크 성공을 모터 루프에서 기다리지는 않는다.
4. **실행 진입점을 정리한다.** 실제 시연은 `care_runtime.py`, 수동 점검은 `pc_dashboard.py`, 통신 모의는 `simulator.py`로 역할을 명시한다. 하나의 로봇에 모터 소유자가 동시에 붙지 않게 한다. 참고용 DB 직접 저장 예제는 실제 경로와 명확히 구분한다.
5. **저장은 목적에 맞게 정리한다.** 로컬 history/events DB와 transport outbox의 이중 이미지 보관, 서버 detection_events와 hazards의 사건/통계 의미를 정의한다. 기존 SQLite 파일을 삭제하는 방식으로 중복을 해결하지 않는다.
