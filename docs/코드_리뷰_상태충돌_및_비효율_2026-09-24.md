# 코드 리뷰: 상태 충돌·예외·비효율

2026-09-24, 앞선 일부 수정이 적용된 현재 작업 트리 기준. 이번 리뷰에서는 실행 로직을 추가로 수정하지 않았다. 아래 `재현`은 실제 모듈을 로컬에서 호출해 문제 동작을 확인했다는 뜻이고, `정적 확인`은 코드의 분기·저장·호출 관계로 확인했다는 뜻이다. 실제 카메라 인식률이나 시연 당시 원인을 확정한 것은 아니다.

## 먼저 고칠 지점

### C01. 이송 완료 상태가 세 계층에서 서로 다름 — 높음, 정적 확인 + 부분 재현

- 서버 `backend/src/main/java/com/deni/backend/device/DeviceMessageService.java:80`은 RELOCATE 성공 시 위험을 ACTIVE로 유지한다.
- 화면 `frontend/src/pages/HazardLocation.tsx:118`은 로컬 `relocationState === 'done'`이면 해결로 취급해 숨긴다. 화면을 나갔다 들어오면 이 상태가 초기화돼 같은 위험이 다시 나타난다.
- 서버 `OperationService.java:44`의 resume은 ACTIVE 삼킴 위험이 있으면 거절한다. 따라서 로봇이 이송 후 자동 주행하더라도, 이후 사용자 일시정지→재개는 막힐 수 있다.
- 로봇은 `hardware/care_controller.py:127`에서 이송 대상 라벨 차단을 해제하지만 `:238`에서 같은 라벨이 보이면 다시 차단한다. `care_runtime.py:32`의 억제는 이송 중 업로드 이벤트만 제어하며, 이송된 물체의 지속적인 안전 위치 상태를 기록하지 않는다.
- 재현: 기존 이송 성공 테스트를 실행한 후 같은 라벨 관측 1회를 추가하니 `SUCCEEDED / RUNNING → HAZARD_PAUSED`가 됐다. 이것만으로 실제로 같은 물체인지 식별할 수 없다는 점도 현재 설계의 한계다.

개선: `ACTIVE / CHECKING / TEMPORARILY_SAFE / RESOLVED`의 서버 상태 전이를 먼저 확정한다. 임시 안전 상태가 재개 차단 대상인지도 같은 정책으로 결정하고 화면·로봇에 적용한다. 모든 같은 라벨을 영구 무시하는 방식은 다른 물체를 놓칠 수 있으므로 피한다.

### C02. 지연 사진이 새로운 위험 사건으로 바뀜 — 높음, 정적 확인

- `hardware/detection/event_store.py:24`에는 촬영 시각이 있으나 `:42 → uploader.enqueue_frame → bridge.py:103` 전송에서 시각을 보내지 않는다.
- `backend/src/main/resources/db/migration/V7__create_robot_input_tables.sql:52`의 트리거는 감지 시각을 수신 시각으로 강제한다.
- `DetectionUploadService.java:51`은 그 시각으로 위험을 만들고, `HazardService.java:153`은 ACTIVE가 없으면 새 건을 만든다.

재현 조건: 제거 전에 촬영 → 업로드 지연 → 제거 성공 → 사진 도착. 이 경우 실제 재관측 없이 새 ACTIVE가 생길 수 있다. 앞서 프론트 완료 시각 비교를 고친 것만으로 이 경로는 해결되지 않는다.

개선: `capturedAt`과 `receivedAt`을 분리하고 세션/프레임 순서를 보존한다. 처리 이전 관측은 이력에는 남기되 처리 이후 새 사건으로 승격하지 않는다. API만 바꾸면 DB 트리거가 여전히 덮어쓰므로 스키마 계약까지 함께 변경해야 한다.

### C03. 기기에 전달되지 않는 제거 요청을 접수 상태로 영구 저장 — 높음, 정적 확인

- `OperationService.java:82`의 직접 제거 경로는 이송과 달리 `requireDelivery(device)`를 호출하지 않는다.
- `:152`의 `queueAction`은 전달 불가이면 예외 없이 return한다. operation_requests에는 접수가 남지만 device_command_delivery에는 행이 없다.
- `:126`의 조회는 계속 `PENDING / NOT_CONNECTED`를 반환한다. dispatcher의 만료 처리는 delivery 행을 대상으로 하므로 이 요청은 만료되지 않는다.
- `HazardLocation.tsx:227`은 FAILED/EXPIRED에서만 대기를 종료하고 NOT_CONNECTED는 처리하지 않는다.

재현 조건: 최근 PAUSED·전원 상태는 유효하지만 소켓은 이미 끊겼거나 모터 제어 가능성이 없는 순간 직접 제거를 요청한다.

개선: 전달 불가이면 접수를 거절하거나, 모든 접수에 전달 행과 만료·재연결 정책을 보장한다. 화면에는 접수됨/전달 대기/결과 미확정을 구분한다.

### C04. 명령 처리 중 예외가 발생하면 결과가 유실됨 — 높음, 재현

- `hardware/bridge.py:215`는 started_commands를 저장하고 `:216`에서 실행한다.
- execute 또는 완료 결과 검증이 예외를 내면 `commands / pending_results` 기록에 도달하지 않는다. finally는 inflight만 제거한다.
- 상위 `:241`은 로그만 남긴다. 재연결의 resend는 pending_results만 읽는다. 프로세스 재시작 시에는 복구 코드가 있지만 살아 있는 프로세스에서 실패한 명령을 마무리하지 않는다.
- 서버는 결국 UNKNOWN으로 바꾸고 `OperationService.java:153`은 UNKNOWN도 busy로 세므로 이후 처리까지 막힐 수 있다.
- 예외 주입 결과: `started_commands=1 / pending_results=0 / inflight=0`.

개선: 예외 후에도 물리 실행 여부를 보존하는 불확정 결과와 복구 상태를 기록한다. 이미 움직였을 수 있으므로 무조건 재실행하거나 성공으로 처리하면 안 된다.

### C05. 간헐적 검출이 계속 누적돼 안정 검출로 확정됨 — 높음, 재현

- `hardware/detection/stabilization.py:17`은 미검출 프레임을 무시한다.
- `risk_engine.py:67`은 검출된 순간에만 투표를 추가한다. 10개 창은 “최근 10프레임”이 아니라 “마지막 양성 관측 10개”다.
- 같은 track ID가 유지되는 합성 입력에서 46프레임 중 10프레임만 검출되고 36프레임은 비어 있어도 stable 이벤트 1건이 생성됐다.
- 앞선 제거 후 이력 초기화 수정과는 별개로, 일반 감지 중에도 발생하는 구조다.

개선: 유효한 미검출 프레임, 관측 시간 범위, 허용 간격을 안정화 정책에 반영한다. 카메라 오류/흐림은 정상 미검출과 구별해야 한다. 임계값 숫자만 올려서는 누적 구조가 사라지지 않는다.

### C06. 로컬 사진 저장 성공과 전송 대기열 등록이 원자적이지 않음 — 높음, 재현

- `hardware/detection/event_store.py:31`에서 사진/이력을 커밋한 뒤 `:42`에서 다른 SQLite의 outbox 등록을 수행한다.
- 후자가 실패하면 로컬 이력은 존재하지만 업로드할 레코드가 없을 수 있다. 로컬 이력에서 누락 outbox를 재구성하는 경로도 없다.
- `risk_engine.py:76`은 저장 성공 전에 cooldown을 갱신한다. 물체가 곧 사라지면 새 이벤트가 발생하지 않아 해당 관측이 서버에 영구 누락될 수 있다.
- 예외 주입 결과: outbox 등록 실패에도 local_history_rows=1.

개선: 이벤트와 전송 상태를 하나의 DB 트랜잭션으로 저장하거나, 동일 eventId로 누락 outbox를 복구하는 재처리 절차를 둔다. 모델 루프에서 저장 오류를 찍는 것만으로 전송이 복구되지는 않는다.

### C07. 화면을 열기만 해도 로봇의 활성 아이가 변경됨 — 높음, 정적 확인

- `RegisteredHome.tsx:135`는 홈 진입의 부수효과로 활성 아이를 변경한다.
- `DeviceService.java:97`은 처리 진행 여부를 확인하지 않고 활성 아이를 바꾼다.
- `DetectionUploadService.java:34`는 촬영 당시 아이가 아니라 업로드 처리 당시 활성 아이를 사용한다. 조회도 뒤쪽 device 잠금보다 먼저 실행된다.

재현 조건: A 아이로 감지·처리 중 다른 탭에서 B 아이 홈을 열거나, 대기 중인 사진을 B 전환 후 전송한다. 감지의 귀속과 사용자가 보고 있는 프로필이 어긋날 수 있다. 로봇 차단은 childId가 없는 라벨 set이라 다른 프로필의 차단이 남는 문제도 있다.

개선: 프로필 선택과 로봇의 감지 세션 전환을 분리한다. 진행 중 전환 정책과 캡처 당시 세션 귀속을 서버가 관리한다.

### C08. 프로필 활성화 실패 후 자동 재시도 주석이 실제로 동작하지 않음 — 중간, 정적 확인

- `RegisteredHome.tsx:138`은 실패 시 ref만 null로 돌린다.
- effect 의존성은 deviceId/isMock/childId뿐이다. 다음 dashboard 응답이 와도 세 값이 같으면 effect는 재실행되지 않는다. ref 변경 역시 재실행을 유발하지 않는다.

개선: 명시적인 retry 함수 또는 제한된 재시도 상태를 사용한다. 단순히 dashboard 객체 전체를 의존성에 넣으면 주기 조회마다 활성화 요청이 발생하므로 피한다.

### C09. 상세 응답이 역순 도착하면 해결 상태가 과거 ACTIVE로 돌아갈 수 있음 — 중간, 정적 확인

- `RegisteredHome.tsx:24`의 newerHazardDetail은 detectedAt만 비교하며 같은 시각이면 새 응답을 채택한다.
- 처리 완료는 detectedAt을 바꾸지 않는다. 폴링(`:160`)은 in-flight 차단이 없고 최초 상세 조회도 별도 경로다.
- A 조회가 과거 ACTIVE를 읽고 지연 → 처리 완료 → B 조회가 RESOLVED 반환 → A가 늦게 반환하면, 시각이 같아서 ACTIVE가 다시 채택된다.
- 수동 `refreshDashboard(:253)`도 주기 조회와 같은 순서 보장을 공유하지 않는다.

개선: 응답의 version/updatedAt을 사용하고, 조회 경로를 통합해 이전 요청을 취소하거나 오래된 응답을 버린다. 프론트에서 RESOLVED를 무조건 영구 우선하는 것보다는 서버 버전을 기준으로 삼아야 한다.

### C10. 처리 요청을 화면 내부에만 기억함 — 중간, 정적 확인

- `HazardLocation.tsx:105`와 `:107`의 actionId는 컴포넌트 state뿐이다.
- 상세에서 나가거나 위험 선택으로 key가 바뀌면 진행 중 요청의 조회를 잃는다. 재진입 시 서버에서 기존 요청을 찾아 복원하지 않는다.
- `frontend/src/services/operations.ts:35`는 재시도마다 새 멱등키를 생성한다. 응답만 유실된 경우 기존 요청을 찾아 이어가지 못한다.
- `HazardLocation.tsx:234`는 조회 오류를 사용자에게 알리지 않고 무한 재조회한다. UNKNOWN의 기기 확인·복구 경로도 없다.

개선: hazardId 기준 현재 action 조회 API와 서버 상태 복원, 사용자 의도별 멱등키 보존, 조회 실패 안내 및 복구 절차를 함께 설계한다.

### C11. 월간 통계가 후속 감지 때문에 과거 월에서 사라짐 — 중간, 정적 확인

- `Hazard.java:122`는 같은 미처리 위험의 detectedAt을 최신 시각으로 갱신한다.
- `HazardRepository.java:35`는 그 변경 가능한 필드로 월을 나누고 hazards 행을 센다.
- 9월 30일 생성된 ACTIVE가 10월 1일 다시 관측되면 같은 행이 10월로 이동해 9월 집계에서 빠진다.

개선: 최초 사건 수를 셀지 관측 이벤트 수를 셀지 정하고, 불변 firstDetectedAt 또는 detection_events로 집계한다. lastSeenAt은 최신 화면 갱신에만 사용한다.

## 권장 수정 순서

1. C01/C03/C04: 이송 완료·전달 실패·결과 미확정의 상태 전이를 통일한다. 모터 명령을 무조건 재실행하는 복구는 금지한다.
2. C02/C06/C07: 촬영 시각·세션·eventId를 끝까지 보존하고 저장/전송의 누락 복구를 만든다.
3. C05: 정상 빈 프레임을 포함한 안정화 정책을 고치고 실영상으로 오탐/미탐을 측정한다.
4. C08~C10: 프론트 비동기 조회와 action 상태를 통합한다.
5. C11 및 반복 저장: 이력 모델·월간 집계·보관 정책을 정리한다.

폴더를 먼저 합치거나 코드를 짧게 만드는 것보다 **상태 판정의 책임과 사건 식별자를 하나로 연결하는 것**이 효과가 크다.

## 재현 결과와 범위

`docs/code_review_repro.py`는 실제 기기/서버에 접속하지 않고, 임시 SQLite·모의 소켓·기존 상태 머신 테스트를 사용한다. 임시 Python 테스트 환경에서 실행했으며 4개 재현 모두 성공했다.

```text
relocation_reblocks: completed=SUCCEEDED, RUNNING -> HAZARD_PAUSED
intermittent_votes: 46 frames / 10 positive / 36 empty -> 1 stable event
history_without_outbox: 1 local history row, enqueue failed
command_exception_loses_result: started=1, pending_results=0, inflight=0
```

이 결과는 문제 동작의 재현 성공이며 수정 후 회귀시험 통과를 뜻하지 않는다. Java/DB 경로와 React 응답 경쟁은 코드 경로 검토로 확인했으며 이번에 실제 서버·브라우저 통합 시험은 수행하지 않았다. 앞선 요구사항 보고서에서 설명한 권한·푸시·임의 지도·재시작 자동 초기화 문제도 여전히 별도 과제다.
