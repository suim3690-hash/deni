# 프론트엔드 → 백엔드·하드웨어 로봇 제어 요청 사항

> 작성일 2026-09-19 | 대상: 백엔드·하드웨어(모델) 담당 | 범위: 로봇 **제어**에 한정

v2 통합 계약은 [Socket 명세](Socket_명세서_백엔드-하드웨어.md), 실제 가능 범위는
[하드웨어 지원 기능표](하드웨어_지원기능.md), 완료 기준은 [통합 테스트](통합_테스트_시나리오.md)에서 관리한다.

## 1. 배경

「모델·하드웨어 DB 저장 가이드」의 `robot_live_state`, `detection_events`와
`GET /devices/{deviceId}/robot-state`, `/detections`, `/detections/{eventId}/image`는 모두 **읽기 전용**이다.
로봇에 명령을 보내고 그 결과를 돌려받는 경로는 아직 없다.

| 현재 상태 | 내용 |
| --- | --- |
| 일시정지 | `POST /devices/{id}/commands/pause`는 접수 기록만 남김 (`deliveryState: NOT_CONNECTED`) |
| 재개 | `POST /devices/{id}/commands/resume`은 항상 `409` (`HAZARD_UNRESOLVED` 또는 `SAFETY_CONFIRMATION_REQUIRED`) |
| 이송 | `POST /hazards/{id}/relocations`는 항상 `409 RELOCATION_NOT_CONFIGURED` |
| 재확인 | `POST /hazards/{id}/removal-checks`는 접수만 하고 결과는 항상 `PENDING`/`UNKNOWN` |
| 제어 가능 여부 | `commandsAvailable`이 항상 `false`, 프론트 제어 버튼은 실제 모드에서 비활성 |
| 상태 입력 | `devices` 상태는 내부 서비스로만 갱신되고 외부 입력 API 없음 |

아래 요청이 해결되기 전에는 프론트가 제어 버튼을 활성화하지 않고 "연동 전" 안내를 유지한다.
요청 접수만으로 성공을 표시하지 않는다 (FR-030: 결과 확인 전 성공 표시 금지).

## 2. 필수 요청 — 제어 기본 경로

| # | 요청 | 프론트에서 필요한 것 | 관련 FR |
| --- | --- | --- | --- |
| 1 | 명령 전달 경로 | 일시정지·재개·정지 명령을 로봇 PC가 받는 경로(명령 테이블 폴링 또는 구독). `commandId`로 상태 추적: `REQUESTED → DELIVERED → SUCCEEDED / FAILED / EXPIRED` | FR-036 |
| 2 | 명령 결과 조회의 실제화 | `GET /devices/{id}/commands/{commandId}`가 실제 `status`, `deviceOperationState`, `confirmedAt` 반환. 성공 판정은 요청 이후 시각의 `robot_live_state` 보고로 확인 | FR-029, 036 |
| 3 | `stop` 명령 정의 | 현재 `pause`/`resume`만 있고 정지는 프론트가 로컬로 흉내냄. 즉시 정지를 `pause`와 같은 명령으로 볼지 별도 명령으로 둘지 확정 | FR-036 |
| 4 | `commandsAvailable` 판정 기준 | `true`가 되는 조건 확정 (기기 온라인, 명령 채널 연결, 최근 상태 보고 등). 프론트는 이 플래그로 버튼 활성화 | FR-002 |
| 5 | 상태 출처 일원화 | `devices`(온라인·배터리)와 `robot_live_state`(동작·이동)가 분리돼 있음. 대시보드 응답에 로봇 동작 상태 포함 또는 `devices`가 라이브 상태 반영. 온라인/오프라인 판정 기준 확정 | FR-001~003 |

## 3. 안전 처리 흐름 요청 (TKS_007)

| # | 요청 | 프론트에서 필요한 것 | 관련 FR |
| --- | --- | --- | --- |
| 6 | 직접 제거 재확인 | `removal-checks` 요청이 모델 PC에 전달돼 재검사가 수행되고, 결과를 `hazardPresent` (`true`/`false`/`null`), `treatmentStatus` (`PENDING → CLEAR / REMAINS / UNKNOWN`), `completedAt`으로 반환. 재검사 타임아웃 정책 포함 | FR-025 |
| 7 | 재개 허용 조건 | 위험물 부재가 확인된 뒤 `resume`이 성공하도록 조건 정의. 실제 `RUNNING` 보고로 재개 확인 | FR-029 |
| 8 | 안전 위치 이동 | 이동 가능 물체, 안전 위치(`safeZoneId`와 좌표), 배터리 기준 확정. 진행 상태는 `RELOCATING` 활용, 완료·실패·미확정 판정 규칙 추가 | FR-026~028 |
| 9 | 배터리 정보 | `robot_live_state`에 배터리 없음. 배터리 부족 시 이동 불가 안내를 하려면 값 필요 | FR-028 |
| 10 | 결과 미확정·재시도 안전성 | 응답 유실 시 상태 재조회로 확인 가능해야 함. 같은 `Idempotency-Key` 재시도로 이동이 재실행되지 않아야 함 | FR-030, 031 |

## 4. 감지와 제어를 잇는 요청

| # | 요청 | 프론트에서 필요한 것 | 관련 FR |
| --- | --- | --- | --- |
| 11 | `detection_events` → `hazards` 연결 규칙 | 지금은 자동 반영되지 않아 홈 알림·위치 확인·처리 버튼이 동작하지 않음. 위험 건에 원본 탐지(`eventId`) 연결, 위험도·위치 `marker`(x, y는 0~1)·`captureImageUrl`(이미지 GET 경로) 채움 | FR-012, 014, 021 |
| 12 | 위험 감지 시 자동 정지 여부 | HAZARD 탐지 시 로봇을 자동 일시정지하는지, 프론트는 알림만 표시하는지 확정. 자동이면 정지 결과도 상태로 조회 가능해야 함 | FR-036 |
| 13 | 자동 이송 모드 설정 API | 위험 상세 화면 토글용. 예: `GET/PUT /devices/{id}/settings` `{ autoRelocation: boolean }`과 로봇 반영 확인. 현재 API가 없어 프론트는 안내 문구만 표시 | FR-026 |

## 5. 공통 계약

| # | 요청 | 내용 |
| --- | --- | --- |
| 14 | 오류 코드 목록 | 프론트 분기용 코드 확정. 예: `DEVICE_NOT_ONLINE`, `COMMAND_TIMEOUT`, `COMMAND_REJECTED`, `BATTERY_LOW`, `RELOCATION_UNAVAILABLE`, `RESULT_UNKNOWN` |
| 15 | 갱신 방식 | 현재 5초 폴링. 명령 결과 대기용 폴링 주기와 최대 대기 시간 확정. 정지 3초 목표라면 SSE·WebSocket 검토 |
| 16 | 접근 권한 (FR-032) | 제어 API는 보호자와 기기 소유 관계를 검증해야 함. 현재 인증이 없으므로 실제 제어 연결 전 최소한 필요 |
| 17 | 안전 처리 이력 | 월간 리포트(FR-038)의 처리 내역을 위해 요청·결과를 이력으로 저장. `robot_live_state`는 최신 한 행만 유지하므로 별도 저장 필요 |

## 6. 우선순위 제안

1. **최소 동작 단위**: 1 → 2 → 4 → 5 (일시정지·정지가 실제로 동작)
2. **안전 처리 핵심 흐름**: 11 → 6 → 7
3. **이동·예외 처리**: 8 → 9 → 10
4. **나머지**: 12, 13, 14~17

## 7. 프론트 반영 계획

| 항목 | 상태 |
| --- | --- |
| 직접 제거 재확인·이송 요청 호출 | 화면에서 실제 API 호출 연결 완료. 현재 서버 응답(접수 대기 또는 `409`)을 그대로 안내 |
| 제어 버튼 활성화 | `commandsAvailable`이 `true`가 될 때까지 비활성 유지 |
| 명령 결과 대기 | 요청 #2 완료 후 `commandId` 상태 폴링 UI 적용 |
| 자동 이송 토글 | 요청 #13 완료 전까지 "아직 지원되지 않아요" 안내 |
| 감지 이미지·위치 | 요청 #11 완료 후 기존 위험 상세 화면에 자동 반영 |
